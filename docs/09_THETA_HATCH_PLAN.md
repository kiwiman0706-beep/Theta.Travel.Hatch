### 他の Hatch との違い
- **最初から Theta 名義で作れた。** Item/Label/DoorPhoto は既存 package と署名の継続が制約だったが、たびのたねは新規なので package・鍵とも Theta 用に揃っている。
- **Web 画面＋薄いネイティブ層の構成。** 画面はそのままブラウザで動くので、T9 のライブデモ・T10 の UI テスト・将来の PC 表示（構想の第3段階）を同じコードで賄える。
- **外部 API への依存が多い。** 地図・位置検索・天気・Gemini・将来の経路/乗換。各サービスの規約・料金・キーの扱いが要件（T9 のプライバシー、配布形態）に直結する。

## 2. 最初に決めること（ユーザー判断が必要）

1. **実機確認を先にするか。** 推奨は「はい」。0.1.0 を `docs/REAL_DEVICE_CHECKLIST.md` で一巡し、不具合を 0.1.x で潰してから Phase 1 以降へ。
2. **主な出発地と交通手段の初期値**（構想の「決めたい点」1）。設定画面で入れられるので必須ではないが、提案と下書きの質に効く。
3. **家族共有の範囲**（同 2）。本人だけなら Phase 4 の同期は「自分の端末間＋PC閲覧」に絞れる。家族の共同編集まで入れるならサーバー（またはGoogleアカウント連携）の設計が必要になる。
4. **過去の旅行記録の初期登録**（同 3）。手入力だけでよいか、写真の撮影日時・位置情報から候補を作る取り込みまで欲しいか。
5. **Gemini キーの扱い。** 個人利用（自分の端末に自分のキー）で十分か、家族や他人にも配る前提でサーバー中継にするか。後者なら Phase 3 で中継（Cloud Run 等）とその費用が要る。
6. **ライセンス**（シリーズに揃えて MIT にするか）。

## 3. 段階的な構想

### Phase 0 — 済（今回）
- 引き継ぎ一式を `docs/handoff/` に無改変で収録。
- 0.1.0 を実装：構想の第1段階（スポット・全スポット地図・提案・しおり・乗換・持ち物・思い出・端末内保存・書き出し・任意の Gemini）。
- 署名鍵を新規作成（リポジトリ外）。`build.yml`（単体・UI・ブリッジテスト、Gradle ビルド・Lint）、`release-apk.yml`（証明書ピン留め検証→Release）。
- v0.1.0 を GitHub Release として公開。

### Phase 1 — 実機確定と CI 署名（T3, T4, T10, T12）
- 実機チェックリストの結果を反映（インセット、音声、共有、写真の向き、戻る操作、実 API）→ 0.1.x。
- `release.yml`：Secrets `TRAVEL_KEYSTORE_B64` 等から鍵を復元し、タグから `assembleRelease -PappVersionName=…`→署名→証明書ピン留め確認→Release。手元ビルドの手順は残す。
- `v0.2.0-beta.1` 形式でベータを1回運用してチャネルを確認。
- エミュレーター E2E（`reactivecircus/android-emulator-runner`）で「起動→スポット登録→再起動後に残る」を最低限確認。

### Phase 2 — 配布と更新（T5, T6）
- アプリ内更新：Releases の APK と `SHA256SUMS.txt` を取得→ハッシュ検証→`PackageInstaller`（`REQUEST_INSTALL_PACKAGES`）。起動時の自動確認は1日1回・オフ可。
- Obtainium で実際に追加・更新できることを確認し、README に手順とスクリーンショット。
- 写真込みバックアップ（ZIP：`tabi-data.json`＋`photos/`）と、ZIP からの復元。機種変更の受入条件を満たす。

### Phase 3 — Theta ブランドと文書・デモ（T1, T8, T9, T11）
- README をシリーズ形式に（ロゴ、Release/Downloads/License バッジ、スクリーンショット、Obtainium 手順）。
- `docs/privacy.html`：保存場所、外部送信先（地図・検索・天気・Gemini・GitHub）と送る内容、Gemini キーの扱い。
- GitHub Pages：LP＋**ライブデモ**（`assets/www` をサンプルデータ入りで公開。保存はブラウザ内のみ）。
- **PC 閲覧（構想の第3段階の前倒し）**：同じ Pages 版で JSON/ZIP バックアップを読み込んで一覧・表・地図を見られるようにする。サーバー不要で「PC で見返す」を先に満たせる。

### Phase 4 — 当日提案の強化（構想の第2段階）
- 天気：時間帯別の降水（Open-Meteo hourly）で「午後から雨」を判定。しおりの日付・目的地の予報を表示し、取得日時を併記。
- 移動時間：直線距離の目安から、経路 API（Google Routes など、要キー・従量課金）による実時間へ。キー無しでは今の目安を継続。
- 施設情報：Places（営業時間・公式URL）を「確認した日時」付きで保存し、訪問前に再確認を促す。
- 公共交通：乗換検索の取得は、利用規約上アプリから使える API があるかを確認してから。無ければ「乗換案内アプリで開く」リンク＋手入力の改善（区間テンプレート、往路から復路の反転作成）。
- 提案：過去の評価・雨の日の満足度・予算・新規/再訪の好みを並べ替えに反映済みの土台を拡張。

### Phase 5 — 端末間・家族（構想の第3段階）
- 2 の判断次第。本人のみ：Google ドライブの通常フォルダ（appDataFolder は PC から見えないため不可）に ZIP 自動バックアップ。家族共同編集：アカウント・権限・競合解決が必要なので別途設計。
- 写真や位置情報からの履歴取り込み（2-4 の判断次第）。
- 日英 UI（T7）：`app.js` の文言を辞書に抽出、端末ロケールで切替。Gemini への指示文も日英で用意。

## 4. 回帰させないこと（Theta 化でも維持）
- ユーザーの発言を最優先（「楽しい感じ」のデザイン、全スポットを地図に、乗換・持ち物を登録できる）。
- 位置を確認できないスポットに自動でピンを置かない。AI・推定・自動取得の情報は「要確認」と取得日時を付け、手入力と区別する。
- 通信がなくても登録済みの情報を閲覧・編集できる。データ形式は `migrate()` で旧版を必ず読める。
- package `jp.theta.travelhatch` と署名鍵の継続。鍵・APIキー・個人の旅行記録をリポジトリに入れない。
